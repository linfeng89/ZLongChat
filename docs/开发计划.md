## 1. 目标与范围

### 1.1 MVP 范围（一句话）

> **跑通「文字倾诉 → AI 秒接缓冲 → 真人接住 → 聊完即散」，并保证求助资源随时可达。**

### 1.2 MVP 做什么

| 能力 | 说明 |
| --- | --- |
| MCP Server | 暴露工具与 UI 资源，任何支持 MCP 的智能体可调用 |
| 文字信号 | 发布 / 浏览 / 接住 / 陪伴，**仅文字** |
| 临时房 | 服务端权威的倒计时、延时、结束缓冲 |
| AI 缓冲 | 秒级接住、身份透明、尽快交给真人 |
| 真人网络 | 在线池、标签匹配、等待窗口、限次 |
| 生成式轻界面 | 倾诉面板 / 信号详情 / 等待窗口 / 临时聊天 |
| 安全兜底 | **规则匹配**后递一张热线卡片；`get_support_resources` 始终可调用（见 §1.6） |
| 举报 | 证据留存、**透明告知**（内容留存的唯一例外） |

### 1.3 MVP **不**做什么（明确排除，防止范围蔓延）

| 排除项 | 理由 |
| --- | --- |
| 语音 / TTS / 变声 / ASR | 不验证核心假设，却引入端侧 SDK、音频审核、对象存储（见产品文档 13.1） |
| 端侧代理 / TEE | 端侧模型 + TEE + 设备适配会拖死 MVP（见 14.2） |
| DID / VC / ZKP | 与「后台实名可追溯」方向相反，移到愿景层 |
| A2A / AG-UI | 协议过早 |
| 情境触发 | 需设备侧投入 |
| Kafka / K8s | 试点规模用不上 |

### 1.4 范围准入规则（硬性）

> **任何新增能力 / 字段 / 指标，必须回答下面两个问题之一，否则不进 MVP。**

| # | 必须回答 | 反例（本项目已砍掉的） |
| --- | --- | --- |
| **R1** | 它**替代了什么现有做法**？ | 端侧变声 —— 没有替代任何东西，只是"更酷" |
| **R2** | 它**解决了什么具体问题**？ | 情绪理解 —— 四个候选用途全都不成立（见产品文档 4.4） |

**补充检查项：**

| 检查项 | 要求 |
| --- | --- |
| 能否用更简单的方式达到同样效果？ | 例：情绪改善度量 → **直接问用户** 比 AI 猜更准 |
| 是否引入了新的隐私面？ | 例：`Signal.emotion` 字段 → 多存一样东西 |
| 是否产生了新的对外承诺？ | 例："100% 识别危机" → 制造持续履行的义务 |
| 是否暗示了某种能力？ | 例：情绪分析 → 暗示"我们在分析你" |

> **这条规则的由来**：本项目的三次范围收缩（端侧变声、DID/ZKP、情绪理解）
> 有一个共同特征 —— 都是**"听起来 AI 产品应该有的能力"**，
> 但都答不上"它到底干吗用"。
>
> 技术选型表最容易犯的错，就是把「看起来该有」当成「需要」。

**记录方式**：被砍掉的能力要写进文档（如产品文档 4.4），
说明**砍它的理由**，避免下次有人再提出来重新讨论一遍。

### 1.5 ⚠️ 前置条件（阻塞项）

| # | 前置条件 | 阻塞什么 | 谁负责 |
| --- | --- | --- | --- |
| P1 | **类目资质调研与主体准备** | **全部开发** | 产品 + 法务 |
| P2 | 心理顾问介入（话术、危机阈值、SOP） | 危机干预模块 | 产品 |
| P3 | 隐私政策与用户协议定稿（含两个留存例外） | 上线 | 产品 + 法务 |

> **P1 未明确前不启动阶段 1 开发。** 这是唯一可能让项目归零的风险。

## 2. 工程结构

### 2.1 复用现有资产（无需重写）

| 需求 | 现有资产 | 复用方式 |
| --- | --- | --- |
| 实时消息 | `ChatHub` / `IMessageTransport` / `SignalRSignalingService` | 直接复用 |
| 在线池 | `IUserConnectionRegistry` / `INodeRegistry` | 加 Redis 实现 |
| 离线消息 / 超时释放 | `IOfflineMessageStore` | 复用同类机制 |
| **AI 缓冲接住** | **`ZLongChat.AiBot`** | **直接复用** —— 它本就是「AI 以 userId 接入 Hub」 |
| AI 抽象 | `IAiAssistant` / `MicrosoftExtensionsAiAssistant` | 复用，换 provider 不改代码 |
| 配置 | `ZLongChat:Client` + `/api/client-config` | 复用并下发给 MCP 客户端 |
| 契约 / 构建 | `ZLongChat.Contracts` / `Directory.*.props` | 复用 |

### 2.2 新增与扩展

```
ZLongChat.Contracts          [扩展] Signal / Session / Retention 模型
ZLongChat.Ai                 [扩展] 共情提示词、安全兜底规则
ZLongChat.API                [扩展] 房间 / 匹配 / 危机 / 举报 / 限次 服务
ZLongChat.AiBot              [复用] 即「AI 缓冲接住」进程
[新] ZLongChat.Mcp           MCP Server：工具 + UI 资源（薄层）
[新] ZLongChat.Proxy        个人情绪代理（MVP 作为服务端组件）
```

### 2.3 新增服务清单（`ZLongChat.API/Services/`）

沿用现有「接口 + 内存实现」风格，便于后续换 Redis / 数据库：

| 服务 | 职责 | MVP 实现 |
| --- | --- | --- |
| `ISignalBus` | 发布 / 广播 / 过期 | 内存 + Channel |
| `IRoomStore` | 临时房生命周期、倒计时（服务端权威） | 内存 + 定时器 |
| `IMatchingService` | 标签匹配 + 在线池选人 | 内存 |
| `IContentModerator` | **审核通路**：L0 规则 + L2 云端审核（异步） | 规则 + 云 API |
| `ISafetyFallback` | **安全兜底通路**：规则匹配 → 递热线卡片（**不做语义识别、不宣称覆盖率**） | 规则词表 |
| `IModerationQueue` | L3 人工复审队列 | 内存 |
| `ISupportResourceStore` | 求助资源（热线）清单，断网/未登录也可取 | 内置静态 |
| `IReportStore` | 举报与证据留存 | 内存 |
| `IRetentionService` | 留存例外标记与**告知记录** | 内存 |
| `IQuotaService` | 倾诉 3 / 倾听 5 限次 | 内存 + 日期窗口 |
| `IAnonymousIdentity` | 手机号实名 ↔ 匿名 ID 映射、**每次会话轮换** | 内存 + 轮换钩子 |

> 审核与安全兜底**必须是两条独立通路**，理由见 `docs/审核与危机识别设计.md` 第 0 节
> —— 耦合会导致「审核 API 故障时兜底卡片也发不出去」的单点问题。
>
> 另注：MVP **不做人工值守**，所以没有 `ICrisisQueue`。
> 兜底通路只做「把一张写着热线的纸条递到用户手里」，不做「持续盯住某个人」。
> ⚠️ 骨架阶段只落了 `ISafetyService`（举报 + 资源 + 规则），
> `IModerationQueue` / `IRetentionService` / `IQuotaService` 仍是待实现。

## 3. 阶段划分与排期

> 顺序原则：**先合规 → 再真人闭环 → 再 AI 缓冲 → 再合规收口**。
> 真人闭环先于 AI，因为核心假设是「陌生人愿意互相接住」，AI 会掩盖这个假设是否成立。

### 阶段 0 · 合规前置（1–2 周）· 阻塞项

| 交付物 | 验收 |
| --- | --- |
| 类目资质结论 | 明确「能上 / 不能上 / 需要什么资质」 |
| 心理顾问签署的话术与危机 SOP | 顾问签字 |
| 隐私政策 / 用户协议（含 13.3 两个例外） | 法务确认 |

**出口条件**：P1 有明确结论。**否则项目停止或转向。**

### 阶段 1 · 协议与真人闭环（3–4 周）

| 工作项 | 交付物 |
| --- | --- |
| 领域模型 | `Contracts` 中 Signal / Session / Room / Report 模型 |
| 房间状态机 | `IRoomStore` + 倒计时（服务端权威） |
| 信号总线 | `ISignalBus` + 广播 |
| 匹配与在线池 | `IMatchingService` |
| 限次 | `IQuotaService` |
| **MCP Server（本次迭代）** | `ZLongChat.Mcp` + 工具契约落地（见第 4 节） |
| 生成式轻界面 | 倾诉面板 / 信号详情 / 等待窗口 / 临时聊天 |
| 接住流程 | **纯真人路径，不含 AI** |

**验收**：真人接住率 > 40%、临时房完成率 > 70%

### 阶段 2 · AI 缓冲层（2–3 周）

| 工作项 | 交付物 |
| --- | --- |
| AI 秒接 | `ai_catch_signal` 服务端自动触发 |
| 共情提示词与边界 | 只共情不建议、不诊断、**不挽留、不制造连续感** |
| 身份透明 | 首条消息必带 AI 标识 |
| 真人切换 | 真人一就位即询问切换 |
| ~~情绪摘要~~ | **已移除** —— 摘要会经过 LLM 且给陌生人看，隐私代价大于收益（详见产品文档 4.4） |
| ~~危机识别~~ | **已移除** —— 措辞一旦声称"识别"，就产生持续履行的义务（见 `docs/审核与危机识别设计.md` §2.4） |
| 安全兜底 | 规则匹配 → 递热线卡片；`get_support_resources` 始终可调用；**不承诺覆盖率** |

**验收**：首次响应 < 5s、AI 缓冲时长中位数 < 10 分钟、AI 身份识别率 100%

### 阶段 3 · 安全合规收口（2 周）

| 工作项 | 交付物 |
| --- | --- |
| 举报与取证 | `IReportStore` + 透明告知 |
| 留存例外 | `IRetentionService` + 告知到达率监控 |
| 内容审核 | L1 同步 + L2 异步分层（见 `docs/审核与危机识别设计.md` §1） |
| 人工复审 | 最小可用审核后台（**举报队列**） |

> ⚠️ 这里**没有**「危机值守 SOP 7×24」。
> MVP 不承诺人工值守 —— 承诺了就要真的 7×24 有人在，
> 否则风险更大（用户以为有人在看，实际没有）。
> 能承诺的只有：**举报会被看到，热线号码随时拿得到。**

**验收**：可上线

### 阶段 4 · 代理与生态（持续）

个人情绪代理（先服务端）、情境触发、生态合作、**v2 语音方案评估**。

### 排期概览

| 阶段 | 周期 | 累计 | 关键出口 |
| --- | --- | --- | --- |
| 0 合规前置 | 1–2 周 | 2 周 | **资质结论（Go / No-Go）** |
| 1 协议 + 真人闭环 | 3–4 周 | 6 周 | 真人接住率 > 40% |
| 2 AI 缓冲 | 2–3 周 | 9 周 | AI 缓冲时长 < 10 分钟 |
| 3 安全合规 | 2 周 | **11 周** | **可上线** |

## 4. 本次迭代：MCP 工具契约（第 1 周）

**目标**：把 `ZLongChat.Mcp` 的接口定死，让后续开发可以并行。

| 任务 | 产出 | 状态 |
| --- | --- | --- |
| 工具清单与分级 | 见契约 §3 总览表 | ✅ 契约 §3 |
| 工具详规（schema / 返回 / 错误） | 见契约 §4 | ✅ 契约 §4 |
| UI 资源清单 | 见契约 §5 | ✅ 契约 §5 |
| 隐私分级与降级策略 | 见契约 §6 | ✅ 契约 §6 |
| 与现有服务映射 | 见契约 §7 | ✅ 契约 §7 |
| 认证与会话上下文 | Bearer token + `CallContextAccessor` | ✅ 契约 §10 Q1 |
| **落地骨架** | `ZLongChat.Core` + `ZLongChat.Mcp` | ✅ 16 工具 / 6 资源可调用 |
| **契约测试** | 工具 schema 快照 | ✅ `tools\mcp-snapshot.ps1` |

**进度详情**：见契约 §11「骨架落地状态」—— 那张表同时列了**已落地**与**明确未落地**，
后者（审核、限流、持久化、真实 widget）不要在后续沟通里被当成已完成。

**为什么先做契约**：MCP 层是薄层，它的形状由产品决定；
契约定死后，后端服务与前端界面可以**并行开发**，不必等彼此。

### 4.1 本次新增的工程结构

```
ZLongChat.Contracts/Shudong/     ← 契约：数据模型 + 错误码 + 工具名 + UI URI 常量
ZLongChat.Core/                  ← 领域：端口（ISignalService / ISessionService / ISafetyService）+ 内存实现
ZLongChat.Mcp/                   ← 适配：Tools / Resources / 鉴权 / 错误映射（薄层）
ZLongChat.API/Program.cs         ← 组合根：AddShudongMcp() + MapShudongMcp()
tools/mcp-{probe,scenario,snapshot}.ps1   ← 三块自检
```

依赖方向严格单向：`API → Mcp → Core → Contracts`。
**`Core` 不知道 MCP 存在**，所以将来要换成 HTTP / gRPC 给客户端用，领域代码零改动。

### 4.2 本次定型的三条硬规则

| 规则 | 落在哪 | 由谁保证 |
| --- | --- | --- |
| 含用户正文的工具一律 `visibility:["app"]` | `[McpMeta("ui", JsonValue = …)]` | `mcp-probe.ps1` 断言 |
| `broadcast` 信号**不可**被接住 | `InMemorySessionService.CatchAsync` | 服务端硬校验 + `mcp-scenario.ps1` |
| 业务异常必须带错误码返回 | `CallToolFilters` → `ShudongErrorPayload` | `mcp-scenario.ps1` 断言 |

> 这三条都是**能自动验证**的，不是写在文档里的君子协定。

## 5. 技术决策记录（ADR）

| # | 决策 | 理由 | 备选 |
| --- | --- | --- | --- |
| ADR-1 | 服务端用 **.NET**（现为 **.NET 10**，2026-09 从 .NET 8 升级） | 现有 6 项目已具备实时/存储/配置/AI 四块能力；.NET 8 LTS 于 2026-11 结束支持 | Go / Node（重写成本高） |
| ADR-2 | MCP 用 **官方 C# SDK** | `ModelContextProtocol.AspNetCore` 2.x 同时支持 net8.0 / net9.0 / net10.0，与 API 同进程 | 跨语言桥接（无必要） |
| ADR-3 | 实时通信用 **SignalR（已有）** | Hub 已实现转发/离线队列/强类型客户端 | MQTT（无必要） |
| ADR-4 | 总线用 **Redis Streams**（起步内存） | 试点规模用不上 Kafka | Kafka / NATS |
| ADR-5 | **MVP 仅文字** | 语音不验证核心假设，却引入三重复杂度 | 端侧变声（成本高） |
| ADR-6 | **常规即焚 + 两个透明例外** | 同时满足隐私承诺与危机/合规责任 | 全留存（违背承诺）/ 全即焚（违法） |
| ADR-7 | 身份用 **手机号实名 + 匿名 ID 分离** | 满足「前台匿名 / 后台可追溯」 | DID（与监管冲突，移愿景） |
| ADR-8 | **AI 是缓冲层，不是陪伴终点** | 产品定位「人类为主」；AI 时长是成本不是成绩 | AI 陪伴为主（定位矛盾） |
| ADR-9 | 个人代理 **MVP 作为服务端组件** | 端侧化会拖死 MVP；接口按可迁移设计 | 直接端侧（风险高） |
| ADR-10 | 工具**敏感内容走 app-only + widget 输入** | 避免倾诉正文进入第三方 LLM 上下文 | 全部 model-visible（隐私风险） |

| # | 风险 | 影响 | 应对 |

**依赖**：

- 外部：类目资质、心理顾问、云内容安全服务
- 内部：现有 `ZLongChat` 工程保持 0 警告基线

## 7. 验收与测试策略

| 层次 | 手段 | 覆盖 | 现状 |
| --- | --- | --- | --- |
| 契约 | **工具 schema 快照测试** | 防止参数/返回结构漂移 | ✅ `tools\mcp-snapshot.ps1` |
| 结构 | 工具数 / `_meta.ui` / 资源可读 / 鉴权 | 协议层不变量 | ✅ `tools\mcp-probe.ps1` |
| 集成 | MCP 客户端 → Server → Core 全链路 | 工具可用性 | ✅ `tools\mcp-scenario.ps1`（13 项） |
| 单元 | 房间状态机、限次、匹配 | 服务端权威逻辑 | ⏳ 阶段 1 |
| 降级 | 无 widget / 无 Tasks 宿主 | 功能不失效 | ⏳ 阶段 1 |
| 安全 | **留存告知到达率** | 合规红线 | ⏳ 阶段 3 |

> ⚠️ 这里**没有**「危机 100% 触发」这一条。产品不做危机识别，也就不能承诺触发率 ——
> 承诺了触发率就等于宣称识别能力，而识别能力是做不到的（见 `docs/审核与危机识别设计.md` §2.4）。
> 能验收的只有：**举报提交后告知一定送达**。
