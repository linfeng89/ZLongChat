## 0. 两个前提（v1.1 修订）

> **前提一：审核 ≠ 危机识别，必须拆开。**
> **前提二：危机识别不是法定义务 —— 它是产品善意，不是责任。**

### 0.1 审核 ≠ 危机识别

这两个需求经常被当成一回事，但它们的**目标、时限、后果**完全不同：

| 维度 | 内容审核 | 安全兜底（原"危机识别"） |
| --- | --- | --- |
| 目标 | 拦违规内容（色情/诈骗/辱骂/引流） | 给可能需要帮助的人递一张写着热线的纸条 |
| **性质** | **法定义务** | ⚠️ **非法定义务** —— 产品善意 |
| 时限 | 可事后（秒级～分钟级） | 越及时越好，但**不承诺** |
| 漏判后果 | 平台被处罚 | 伦理遗憾 + 舆情风险 |
| 覆盖要求 | **100% 扫描**（法定） | **不承诺覆盖率** |
| 是否对外宣称 | 可（合规需要） | ❌ **不宣称、不承诺** |

**结论：绝不共用一条链路。**

如果两者耦合在一个同步审核调用里，会同时踩两个坑：

- 审核 API 故障 → 安全兜底也失效（**单点**）
- 安全兜底被迫等待审核结果 → 用户在最需要帮助时被延迟

### 0.2 ⚠️ 纠正一个此前的过度表述

本文 v1.0 曾把危机识别定性为「**法律责任**」，这个说法**不准确**，必须纠正：

| ❌ v1.0 的说法 | ✅ 准确的说法 |
| --- | --- |
| 危机识别是法律责任 | **法律没有要求任何平台必须做危机识别。** |
| 不做就是违法 | 不做**不违法**，但会有伦理与舆情代价 |
| 承诺 100% 触发 | **不能承诺**；承诺了反而制造义务 |

**参照物：微信不为用户的聊天内容导致的事故担责。** 因为它是**通道** ——
它不主动撮合、不知情、无承诺。

**那这个产品为什么仍然建议做安全兜底？三个理由：**

1. **伦理** —— 真的可能帮到一个人，成本极低
2. **舆情** —— 一次事故的代价是品牌级（不是法院判赔）
3. **一致性** —— 如果产品对外暗示"关注你的情绪"，不做会显得言行不一

**但关键是：做的方式决定了它是否产生义务。**

| 做法 | 是否产生义务 |
| --- | --- |
| 宣称"我们识别危机、100% 转介" | ✅ **产生持续履行的义务**，做不到反而更糟 |
| 放一张随时可取的热线卡片，不宣称 | ❌ 不产生义务 |

**所以本设计的选择是：做轻量兜底，但不宣称、不承诺。**

## 1. Q3 · 内容审核

### 1.1 用户的原始问题

> 内容审核用 AI 审核还是人工？每条信息都需要审核？

两个子问题，分别回答。

### 1.2 「每条都审」是对的，但**必须分层**

先看朴素做法的代价。若每条消息都**同步**调用云审核 API：

| 问题 | 表现 |
| --- | --- |
| 延迟 | +200–500ms/条；30 分钟会话约 60 条，用户明显感到卡顿 |
| 成本 | 按条计费，与消息量线性增长 |
| **可用性** | 审核 API 故障 = **全站聊不了天**（不可接受） |

但若只审「发布信号」、不审会话消息，又会漏掉这个产品最怕的东西：
**会话内的骚扰、诈骗、联系方式交换**。

所以答案是：**每条都审，但按风险分层、按类型分同步异步。**

### 1.3 分层方案

| 层 | 手段 | 覆盖 | 延迟 | 模式 | 处置 |
| --- | --- | --- | --- | --- | --- |
| **L0 规则** | 正则 + 词典：手机号、微信号、QQ、URL、违禁词 | **100% 消息** | < 1ms | **同步** | 命中即拦截 / 打标 |
| **L1 危机识别** | 见第 2 节 | **100% 消息** | 规则同步 / 语义准同步 | 独立通路 | 触发热线 + 人工 |
| **L2 云端审核** | 文本内容安全 API | **100% 消息** | 200–500ms | **异步** | 命中则冻结会话 + 人工 |
| **L3 人工复审** | 人 | 仅 L1/L2 命中 + 举报 | — | — | 处置决策 |

> **「每条信息都审核」= 每条都过 L0 + L1 + L2。**
> 区别只在于 **L2 是异步的**，L0 是同步的，L1 独立。

### 1.4 为什么 L2 可以异步

| 理由 | 说明 |
| --- | --- |
| 危害面小 | 会话是**双盲私密**的，只有对方看到，不是公开发布 |
| 窗口期代价低 | 最坏情况是用户多看到一条消息（1–3 秒后被冻结） |
| 换来可用性 | 审核 API 故障不阻塞聊天 |
| 换来体验 | 消息零延迟 |

**对比：为什么「发布信号」必须同步**

| 理由 | 说明 |
| --- | --- |
| 危害面大 | 进入**公共池**，可能被多个倾听者看到 |
| 频率低 | 3 次/日，延迟完全可接受 |
| 一次审核收益最高 | 一次投入挡住公开传播 |

### 1.5 AI 还是人工？—— **不是二选一，是 AI 筛 + 人工判**

| 角色 | 覆盖 | 优势 | 劣势 |
| --- | --- | --- | --- |
| **AI**（L0 规则 + L2 云 API） | 100% | 零延迟、成本低、不漏扫 | 误判率高、不懂语境 |
| **人工**（L3） | 仅命中项 | 准确、能判语境与意图 | 成本极高，**不可能覆盖全量** |

**成本对比（关键论据）**

假设日活 1000 人、人均 30 条消息 = **3 万条/天**：

| 方案 | 人力 | 可行性 |
| --- | --- | --- |
| 全人工审核 | 审核员日均处理 2000–3000 条 → **需 10–15 人** | ❌ 不可持续 |
| AI 全量 + 人工复审（命中率按 1% 估） | **300 条/天 → 1 人可覆盖** | ✅ 推荐 |

**必须 100% 人工的（AI 只做前置筛查，不做最终判定）：**

- **危机事件** —— 人工介入是法定动作，不能被自动化替代
- **举报** —— 必须人工复核后才可处置
- **AI 判定为高风险**的项

### 1.6 同步 / 异步 决策表

| 内容 | L0 规则 | L2 云审核 | 理由 |
| --- | --- | --- | --- |
| 倾诉信号正文 | ✅ 同步 | ✅ **同步** | 进公共池、频率低 |
| 会话消息 | ✅ 同步 | ⏳ **异步** | 高频、私密、延迟敏感 |
| 举报证据 | — | — | **人工 100%** |
| 危机命中 | ✅ 同步 | — | 走独立通路，见第 2 节 |

### 1.7 结论

| 问题 | 结论 |
| --- | --- |
| AI 还是人工？ | **AI 做筛、人工做判**。AI 覆盖 100%，人工只处理命中项（< 1%），危机与举报 100% 人工 |
| 每条都要审吗？ | **是** —— 但 L0 同步、L2 异步、L1 独立通路 |
| 关键设计 | **审核不能阻塞消息**，否则审核 API 成为全站单点 |

## 2. Q4 · 安全兜底放端侧还是服务端

> **本节已按 v1.1 修订**：从「危机识别系统」降级为「**安全兜底**」。
> 措辞变化不是文字游戏 —— 它决定了平台是否承担持续履行的义务。

### 2.1 结论

> **服务端做规则匹配并展示热线卡片；端侧只做本地静态资源。**
> **两者都不宣称"识别危机"，也都不承诺覆盖率。**

用户的直觉（"服务端更全面精确"）方向是对的 —— 平台能看到的内容只在服务端，
所以**任何服务端能做的，端侧都做不了**。

但更重要的是：**做多少，取决于你愿意承担多少义务。** 见 2.4。

### 2.2 为什么服务端（而非端侧）

| # | 理由 | 说明 |
| --- | --- | --- |
| 1 | **内容本来就在服务端** | 状态 2/3 的内容进池，服务端天然能看到；端侧看不到别人的内容 |
| 2 | **状态 1 端侧也做不了** | 状态 1 内容不上传，服务端看不到 —— 所以**状态 1 不做任何识别**（见 2.5） |
| 3 | **多设备一致** | 用户在手表说一句、手机说一句 —— 端侧各自处理无法拼出完整图景 |
| 4 | **与现有架构一致** | 内容全走服务端（不用 P2P）的同一个约束 |
| 5 | **可关闭** | 服务端改配置立即生效；端侧要等用户升级 App |

> **注意：这里不再列"语义模型能力""人工介入""可审计"等理由** ——
> 因为 MVP **不做语义模型、不做人工值守**（见 2.4）。
> 保留理由会让方案看起来比实际更重。

### 2.3 端侧不可替代的两件事

| 事项 | 端侧 | 服务端 |
| --- | --- | --- |
| **状态 1 的内容** | ✅ 只有端侧有 | ❌ 看不到 |
| **静态热线资源** | ✅ 内置，**断网也能用** | ➖ |
| **生理信号**（愿景） | ✅ 采集，只上报风险等级 | ➖ 不接收原始数据 |

**关键区分：**

- 端侧负责「**你随时能拿到一张写着热线的纸条**」—— **不依赖网络、不做识别**
- 服务端负责「**内容进池时顺手看一眼有没有明显信号**」—— 规则匹配，非语义模型

生理信号不上传是产品承诺（文档 10.3），但端侧检测到极端异常时可以**本地**主动建议求助 ——
这**不需要上传任何数据**。

### 2.4 ⚠️ 措辞决定义务：为什么不做承诺

**这是本节最重要的一条，也是 v1.1 修订的核心。**

**「100%」这个数字本身就是陷阱：**

| 表述 | 后果 |
| --- | --- |
| ❌ "我们 100% 识别危机" | **产生持续履行的义务**。漏判一次，先前的承诺就成为对你不利的证据 |
| ❌ "危机转介触发率 100%" | 同上。而且用户会以为"系统在盯着我" |
| ✅ "这里有一张写着热线的纸条，你需要就拿走" | **不产生义务** |

**为什么不能承诺识别率：**

- 用户不通过我们的渠道说话 → 我们看不到
- 用户用隐喻表达、或只发一个表情 → 规则匹配不到
- 用户选状态 1（说出来就好）→ **内容根本不上传，物理上看不到**

**所以本设计的选择：**

| 项 | 决定 |
| --- | --- |
| 对外宣传 | ❌ **不提及任何识别能力** |
| 对外指标 | ❌ **不设识别率指标** |
| 内部实现 | ✅ 规则匹配 + 展示热线卡片（**成本极低**） |
| 可验证性 | ✅ 只验证「**热线资源可用率**」这类事实性指标 |

> **把「识别能力」从承诺降为"顺手做的事"，是本次修订最有价值的一条。**
> 它同时降低了法律风险与工程成本，而且**不影响实际帮到人的概率**
> —— 那张热线卡片该出现时还是会出现。

### 2.5 离线兜底（端侧，不依赖网络）

**端侧内置静态危机资源**，任何界面、任何状态都能一键取到：

- 12356 全国心理援助热线
- 110 / 120
- 本地心理机构联系方式（若已配置）

即使完全断网，用户也能看到这些号码。这是**纯静态资源**，不涉及任何隐私上传。

### 2.6 技术方案：双通 + 快慢分离

```text
用户消息进入
    │
    ├─【通路 A · 危机】───────────────────────────────
    │   A1 规则匹配（同步，<1ms）
    │       命中 → 立即触发热线（不等语义结果）
    │   A2 语义识别（准同步，1–2s，LLM）
    │       命中 → 触发热线 + 人工介入 + 留存告知
    │
    └─【通路 B · 审核】───────────────────────────────
        B1 规则（同步，<1ms）—— 联系方式/URL/违禁词
        B2 云内容安全（异步，200–500ms）
            命中 → 冻结会话 + 人工复审
```

**为什么危机走「准同步」而不是「异步」**

危机场景下用户需要**立刻**看到热线。1–2 秒可接受（用户还在打字/等待回复）；
但**绝不能等到会话结束才处置**。

**为什么两条通路必须独立**

| 理由 | 说明 |
| --- | --- |
| 可用性要求不同 | 审核 API 故障时，**热线卡片必须仍然能展示** |
| 代价不同 | 审核漏判 = 平台被处罚；兜底漏判 = 伦理遗憾 + 舆情 |
| 迭代节奏不同 | 危机阈值调整频率远高于审核规则 |

### 2.7 结论

| 问题 | 结论 |
| --- | --- |
| 端侧还是服务端？ | **服务端做判定**；端侧只做生理/行为信号的**建议触发** |
| 为什么 | 语义能力、人工介入、可迭代、可审计、多设备一致、架构一致 |
| 端侧的不可替代价值 | ① 生理信号（隐私要求不上传）② **断网时的静态热线兜底** |
| 必须精确化的措辞 | 「100%」应限定为**对可见内容的识别流程执行率**，而非识别准确率 |

## 3. 两条通路的关系（小结）

| | 通路 A · 危机 | 通路 B · 审核 |
| --- | --- | --- |
| 触发条件 | 每一条消息 | 每一条消息 |
| L0 规则 | ✅ 同步 | ✅ 同步 |
| 识别手段 | **规则匹配**（同步，MVP 不做语义模型） | 云 API（异步 200–500ms） |
| 命中处置 | 展示热线卡片（**不留存、不告知**） | 冻结会话 + 人工复审 |
| 故障影响 | 不影响（只是不展示卡片） | 可暂时积压 |
| 人工介入 | ❌ MVP 不做 | 命中项才介入 |

**共同点**：**只有举报会触发留存与告知**（产品文档 13.3 的唯一例外）。
安全兜底**不留存**、**不告知** —— 它只是展示一张卡片。

## 4. 服务与接口

| 服务 | 职责 | 对应通路 |
| --- | --- | --- |
| `IContentModerator` | L0 规则 + L2 云端审核（异步） | B |
| `ICrisisDetector` | A1 规则 + A2 语义 | A |
| `IModerationQueue` | L3 人工复审队列 | B |
| `ICrisisQueue` | 危机人工值守队列（**最高优先级**） | A |
| `IRetentionService` | 命中即标记留存 + 记录告知 | A + B |

**配置项（走现有 `ZLongChat:Client` 风格下发）**

```jsonc
"Shudong": {
  "Moderation": {
    "RuleSyncEnabled": true,
    "CloudAuditAsync": true,
    "CloudAuditProvider": "tencent|aliyun",
    "BlockContactExchange": true          // 联系方式交换：产品硬规则
  },
  "Crisis": {
    "RuleSyncEnabled": true,
    "SemanticEnabled": true,
    "SemanticTimeoutMs": 2000,
    "FailOpen": true,                     // 语义超时/故障时不阻断对话
    "StaticResourcesOffline": true         // 端侧内置热线，断网可用
  }
}
```

> **`FailOpen: true` 的含义**：危机语义识别超时或故障时，**不阻断用户对话**，
> 只记录待复核。理由：危机场景下"聊不下去"比"漏判一条"伤害更大。
> 但规则层命中不适用 FailOpen —— 规则是同步且廉价的。

## 5. 责任边界与角色定位

> 本节是 v1.1 讨论的核心产出：**说不清自己是什么角色，就说不清自己有什么义务。**

### 5.1 三层类比

| 类比 | 平台角色 | 平台知道什么 | 义务 |
| --- | --- | --- | --- |
| 微信 | **通道** | 什么都不知道 | 最低 |
| **匿名论坛 / 告白墙** | **场所** | 内容被匿名发布 | **内容审核（法定）** |
| 交友 / 婚恋平台 | 主动配对 | 用户意图 + 撮合 | 安全保障（较重） |

**本产品三个状态的落点：**

| 状态 | 类比 | 平台角色 | 义务 |
| :---: | --- | --- | --- |
| **1 · 说出来就好** | 私人日记 | **无** | **无**（内容不在平台） |
| **2 · 被听到** | 匿名墙 | 场所 | **内容审核** |
| **3 · 需要陪伴** | 匿名墙 + 连接机制 | 场所 + 连接 | 内容审核 + **轻度连接注意** |

> **状态 3 也只是"轻度"** —— 因为连接由**倾听者自愿响应**，
> 平台明确「不派单、不抢单、无积分」，**没有主动配对行为**。

### 5.2 为什么不是"通道"（不像微信）

微信不担责，是因为它**不知情、不撮合、无承诺**。对照：

| 维度 | 微信 | 本产品 |
| --- | --- | --- |
| 内容流向 | 用户点对点 | 内容进池，**可能被多个匿名陌生人看到** |
| 平台是否看到内容 | ❌ | ✅ **看得到**（状态 2/3） |
| 是否有连接机制 | 用户自有关系 | **平台提供广播与连接机制** |
| 是否有对外承诺 | ❌ | ⚠️ **取决于话术** ← **唯一可控变量** |

**结论：本产品不是"通道"，是"墙"（状态 3 再加一层连接机制）。**
义务比微信重，但明显比交友平台轻。

### 5.3 唯一可控的变量：话术

前三条由产品形态决定（改不了），**只有第四条完全由我们控制**。

| 说法 | 义务 |
| --- | --- |
| ❌「情绪接住网络」「1 分钟被接住」「AI 随时陪你」 | **高** |
| ✅「一个树洞。你可以说出来，也可以让人看到，也可以让人陪你一会儿」 | **低** |

**行动项**：所有对外文案过一遍「**这句话是不是在承诺**」。
（禁止文案清单见产品文档 18.1）

### 5.4 风险排序（真正要防的是什么）

| 风险 | 真实程度 | 说明 |
| --- | --- | --- |
| 刑事 | **极低** | 除非涉及教唆 / 帮助自杀等极端情形 |
| 民事赔偿 | 真实 | 看「是否尽到合理注意义务」 |
| 行政处罚 | 真实 | 网信约谈、罚款 |
| **平台下架** | **真实** | 舆情后应用商店主动下架 |
| **声誉** | 🔴 **最高** | 一次事故 = 品牌终结级 |

**对这个产品，最大风险不是法院判赔，而是「事故 + 舆情 → 下架」。**

所以安全兜底的价值不是"免责"，而是三件事：
**伦理**（真的可能帮到人）、**运营可持续性**、**融资与合作**（投资人与心理机构一定会问）。

### 5.5 《精神卫生法》红线

| 项 | 要求 |
| --- | --- |
| 产品定位 | 必须是**陪伴 / 倾听**，**不是咨询 / 治疗** |
| 不做 | 诊断、治疗建议、专业能力宣称 |
| 性质 | **法律必需**，不是产品偏好 |

> 这也是产品文档把「不做心理咨询平台」列为**非目标**的原因 ——
> 它同时是产品定位和法律边界的双重声明。
